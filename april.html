Pancake sort

You may only flip the top k pancakes.

  1. find the largest pancakek = index of the largest
  2. flip it to the topflip(k + 1)
  3. flip it to the bottomflip(n)
  4. repeat on the restn = n − 1, repeat
// Slide 3. Four beats. You have a stack of pancakes of different sizes and one tool, a spatula. You can slide it in anywhere and flip everything above it: the top k pancakes. That's the only move. The goal is to sort the stack, biggest at the bottom. [1] Step one: find the largest pancake in the part you haven't sorted yet. Here it's the 4. [2] Step two: flip it to the top. [3] Step three: flip the whole unsorted part. Now the largest is at the bottom, and we never touch it again. [4] Step four: repeat on the rest. On this particular stack, the rest is already sorted. One round happened to be enough. Remember that—it will matter later. Four steps. Keep those in mind.

// Slide 4. Four beats. Head on the left; example cards on the right. // Treat the diagram as a simplified model, not a literal pipeline. Here's a simplified way to think about that gap. [1] You encounter some information: an array, a line of code, an explanation. Short-term memory lets you briefly hold onto it. [2] Working memory is where you actively work with that information. Hold the position of the largest pancake. Work out what the flip changes. Remember which part is already sorted. But working memory has limited room. [3] What you already know, in long-term memory, makes a difference. If you know Rust, a range or a slice is a familiar chunk. If you don't, understanding the syntax competes with understanding the algorithm. Part of expertise is having those chunks—and knowing when to use them. [4] A chatbot can give you the finished program without requiring you to predict, test, or revise anything. You can still learn from it, but getting the answer doesn't mean you've done the thinking that builds that expertise. Our little poll put some of the thinking back. You had to commit to a prediction. So the question for the tools today is: how do we give learners something to think with, inspect, and revise?
A principle

Make thinking debuggable.

Externalize it early. Keep it low-fidelity. Let it be wrong.

// Slide 5. Three beats, one line each. That gives me my principle: make thinking debuggable. Seeing the code is a start. Debuggable means being able to locate a problem in your understanding and do something about it. Three things follow. [1] Externalize it early. Get the thinking out of your head while you're still forming the solution: a plan, a sketch, a sentence. [2] Keep it low-fidelity. Cheap enough to change, but concrete enough that it can be wrong. [3] And let it be wrong. Give learners a way to discover the problem and revise their own approach. Today, that feedback will take several forms: a label, an explanation, a failing input—and a puppy walking off the screen.

int n = 4;
float[] ys = new float[n];

void pancake(float x, float y) {
  fill(200, 138, 58);
  ellipse(x, y + 10, 200, 70);   // edge
  ellipse(x, y, 200, 70);        // top
  fill(139, 74, 18);
  ellipse(x, y - 6, 144, 44);    // syrup
  rect(x - 40, y, 6, 30);        // drips
  rect(x + 10, y, 6, 40);
  fill(240, 200, 60);
  rect(x - 14, y - 30, 28, 18);  // butter
}

void draw() {
  for (int i = 0; i < n; i++)
    ys[i] = height/2 - i*24;
  for (int i = 0; i < n; i++)
    pancake(width/2, ys[i]);
}

// Slide 12. Static. About thirty seconds. Three tools, two questions: how does the learner express their thinking, and how can they check it? DBox: a plan in words, with feedback on its steps. Plan Tracing: concrete states alongside those words. Helpful for learners' reasoning, but the AI feedback remained a problem. SketchMind: executable actions, with a counterexample replayed through the learner's own procedure. Across these designs, we moved toward feedback the learner could inspect directly. Make thinking debuggable: externalize it early, keep it cheap to revise, and make mistakes useful. But everything so far has focused on one learner and one machine.
