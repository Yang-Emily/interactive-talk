Hi everyone, I'm Yang Wu from ETH Zurich. This is joint work with Clément Pit-Claudel at EPFL and April Wang at ETH. Today I'll talk about SketchMind, a system where you build a sorting algorithm by drawing on an execution trace with a pen.
01Motivation

When learning algorithms, we often trace them with pen and paper,

but these traces can get long and go wrong.

Every state is redrawn by hand, nothing groups the steps, and nothing checks the result.

02SketchMind

Supporting algorithmic reasoning through executable sketching

aExecutable tracing
bReusable pens
cMulti-level trace views
dCounterexamples
SketchMind runs on a tablet with a stylus, and it has four capabilities. (a) Executable tracing: pen strokes become operations that execute and get recorded as trace steps. (b) Reusable pens: you merge parts of the trace into your own pens. (c) Multi-level trace views: the same trace shown in terms of values, indices, or parameters. (d) Counterexamples: the system replays your procedure on a nearby input where it fails. Let's see them on the real system.
aExecutable tracing

SketchMind turns learners’ sketches into executable plans.

Write the input with the Data pen.

Handwritten digits become an array. A trace card records it.

Pick Compare, stroke across 3 and 1 → is_bigger(3, 1).

Swap the same pair. The numbers move; no redrawing.

Free-form strokes perform operations. The trace grows step by step.

Steps merge into Compare & Swap and Bubble up pens: a replayable record of the reasoning.

// Five beats; each plays one segment of the screen recording and pauses. SketchMind turns these sketches into executable plans. [1] The learner writes 3, 1, 4, 2 with the Data pen. The digits are recognized and become an array, and the first trace card appears. [2] They pick the Compare pen and draw across 3 and 1. The values get a halo, and a card records is_bigger(3, 1) = true. [3] Swap pen on the same pair. The numbers actually move, and a swap card is added. Nothing is redrawn. [4] They continue: compare 3 and 4, compare 4 and 2, swap. Strokes can have any shape; what matters is which numbers they cross. [5] Then they merge steps into their own pens, Compare & Swap and Bubble up, and apply two passes: 1, 2, 3, 4. Every stroke is now a typed, persistent step that can be replayed, inspected, and revised. That addresses C1.

// Three beats. For C2, SketchMind lets learners compose trace steps. As in the demo, the learner drags the swap card into the true branch of is_bigger. That builds a conditional, and it's promoted to a new pen: Compare and Swap, which applies to any pair with one stroke. [1] Applying compare-and-swap along adjacent pairs gives a Bubble up pen, one full pass. [2] Repeating bubble up on a shrinking range gives Bubble Sort, a nested loop. Participants described these pens as functions they had defined themselves. [3] The same mechanism works for other algorithms. In pancake sort, find_max feeds the index into flip.

// Two beats. To get from a concrete example to a general rule, SketchMind shows the same procedure in three coordinated views. The value view shows what happened on 3, 1, 4, 2: 3 and 1, then 3 and 4, then 4 and 2. [1] The index view shows where it happened: a[0] and a[1], then a[1] and a[2]. // Two beats; plays the counterexample part of the screen recording. Now C3. The learner's plan, two Bubble-up passes, sorts 3, 1, 4, 2. So they are done, or think they are. [1] They press Done. Instead of a list of random test cases, SketchMind changes their example as little as possible: "Your example looks great, but what if we change 2 to 0?" [2] Then it replays their own plan on 3, 1, 4, 0. Same comparisons, same swaps, same path. The result is 1, 0, 3, 4. Not sorted. The system doesn't fix it. It says the array is not fully sorted yet and asks them to take another look at the steps. The failure is on an input almost identical to theirs, so they can see where the reasoning stops: a third pass is missing.

// Two beats: the result row, then the pass the plan is missing. How did SketchMind come up with 2 → 0? We compile the learner's plan into SMT constraints. Each card becomes a constraint on the array state. We ask the solver for an input where every comparison comes out the same way as in the learner's run, so the replay follows the same path, but the final array is not sorted. Among those inputs, we minimize the L1 distance to the original. Look at the columns: every check and cross matches. Only the last number changed. [1] Yet the result is 1, 0, 3, 4 instead of sorted. [2] The comparison that would fix it, 1 > 0, belongs to a third pass, and that pass is exactly what the plan is missing. Z3 finds this in a fraction of a second.
02Implementation

Three layers

Sketch layer
  • Data pen: handwritten digits → array slots
  • Operation pens: the pen picks the operation, the stroke picks the elements
  • Gestures: merge / split cards
Gemini 3.0 Flash · digit recognition
Execution engine
  • Versioned step sequence
  • Insert / delete → downstream recompute
  • Multi-instance replay with original ink
React · TypeScript
Symbolic engine
  • Compile trace → SMT-LIB
  • Check correctness
  • Find the closest failing input
Z3
↩ the counterexample comes back as a new instance to replay
// Static. Keep it short. Briefly, the implementation. The sketch layer recognizes handwritten digits and maps strokes to operations. Stroke shape doesn't matter; what counts is which elements the stroke crosses. The execution engine keeps a versioned sequence of steps and replays them across instances. The symbolic engine compiles the trace to SMT, and the counterexample it finds is added back as a new instance the learner can practice on.

Here's everything together on an algorithm most people haven't seen: pancake sort. You may only flip the top k pancakes. [1] The learner writes 2, 3, 4, 1 with the Data pen. A trace card appears. [2] find_max pen across all four: the 4 lights up. [3] flip pen across the first three: the 4 comes to the front. [4] flip across all four: 1, 2, 3, 4. Sorted, after one round. [5] Check. Instead of an explanation, the system suggests a small change to the input. [6] One tap: the input becomes 3, 2, 4, 1. Same procedure. [7] Replay: find max, flip three, flip all. 1, 3, 2, 4. [10] Then the first two. Sorted. [11] Now the views. [12] Index view: the rounds have the same structure; only the range changes. [13] Merge the rounds into a loop: pancake_sort. [14] Parameter view: i from n−1 down to 1. That's pancake sort, and the learner can point at every line and say where it came from.

We ran a preliminary study with 20 participants: 15 students and 5 instructors, in person on an iPad with a pencil. Stage one used bubble sort, which everyone knew, with four guided tasks that each introduced one feature. Stage two used pancake sort, which nobody knew, not even the instructors. Participants built their own solution while thinking aloud. In both stages they sketched on paper first, which gave us the paper sketches you saw earlier. Finally, a survey and an interview.

04Discussion

Toward a general SketchMind

reused across algorithmscanvas · trace · replay · pen composition · counterexample pipeline
per algorithmprimitive pens · visual model · views · SMT predicates
  • Bubble → Pancake reused the infrastructure; it added range selection, find_max and flip.
  • Learners' own visual language (bars, circles, bubbles) is a cue we don't use yet.

Limitations

  • Proof of concept: two array-based sorting algorithms with local, sequential operations.
  • Learners compose pens, but cannot define new primitives.
  • The minimal change is not always the most instructive one.
  • We measured usability, not learning outcomes. No transfer, retention, or control group.
// Two beats. What would a general SketchMind take? The canvas, the trace, replay, composition, and the counterexample search carry over between algorithms. Going from bubble to pancake reused all of them. What's specific to each algorithm are the primitive pens, the visual model, the views, and the SMT predicates. [1] Participants also drew bars, circles, and bubbles. A future system could interpret that visual language. [2] Limitations: this is a proof of concept for two sorting algorithms. Learners can't define new primitives. The smallest change isn't always the most instructive one. And we studied usability, not learning gains.

// Optional. Drop this slide if time is short. One question we often get: why not just ask an LLM? We're testing that now. On 50 bubble sort cases, recent models like Gemini 3.8 Flash and GPT-5.5 found valid counterexamples every time, but took 15 to 20 seconds each. GPT-4o did poorly and said a counterexample existed even for correct algorithms. SMT runs in a third of a second.
